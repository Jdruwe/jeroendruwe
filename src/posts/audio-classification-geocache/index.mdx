I built a geocache that asks people to imitate a chicken. Cachers scan a QR code, get redirected to [toktoktok.pages.dev](https://toktoktok.pages.dev/), and make chicken sounds into their phone. The browser uses Google's MediaPipe to classify the audio in real-time. If the attempt is convincing enough, they get the combination to unlock the container.

This post covers how I built it, from capturing audio with the Web Audio API to running machine learning models in the browser.

## Geocache

If you're not familiar with geocaching, it's an outdoor treasure hunt using GPS coordinates. Someone hides a container, posts the coordinates online at [geocaching.com](https://www.geocaching.com/), and others use their phones or GPS devices to find it. There are over 3 million active geocaches worldwide.

Most are straightforward: find the container, sign the logbook, move on. But puzzle caches require solving challenges before you can access the container. These usually involve riddles, ciphers, or math problems solved at home before heading outside.

## Capturing Audio

The first step in building the audio classification system was getting access to the user's microphone. This is handled by the [Media Capture and Streams API](https://developer.mozilla.org/en-US/docs/Web/API/Media_Capture_and_Streams_API), which provides a standardized way to access media input devices in the browser.

The core of this API is [`getUserMedia()`](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia), a method that prompts the user for permission to access their microphone or camera. When you call it with `{ audio: true }`, the browser shows a permission dialog. If the user approves, you get a [`MediaStream`](https://developer.mozilla.org/en-US/docs/Web/API/MediaStream) object containing the audio track from their microphone.

```tsx
const stream = await navigator.mediaDevices.getUserMedia({ audio: true });
```

## Recording Audio

Once I had access to the microphone input, I needed a way to actually record and store the audio. [MediaStream Recording API](https://developer.mozilla.org/en-US/docs/Web/API/MediaStream_Recording_API) to the rescue.

The [`MediaRecorder`](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder) interface takes a `MediaStream` and records it into chunks of data. You attach event handlers to collect these chunks, and when recording stops, you combine them into a single audio file (typically a Blob) that can be played back or sent to a server.

Here's how MediaRecorder works in practice:

1. Get a MediaStream from `getUserMedia({ audio: true })`
2. Create a MediaRecorder instance with that stream
3. Attach event handlers for `ondataavailable` and `onstop`
4. Call `recorder.start()` to begin capturing
5. Collect chunks in `ondataavailable`
6. Call `recorder.stop()` when the user is done
7. In `onstop`, combine chunks into a Blob and create an object URL

Here's a basic recording demo to see it in action:

<NoProse>
  <AudioRecorder client:load />
</NoProse>

```tsx
// use-audio-recorder.ts
const audioChunksRef = useRef<Blob[]>([]);

const createMediaRecorder = (stream: MediaStream) => {
  const recorder = new MediaRecorder(stream);

  recorder.ondataavailable = (e) => {
    if (e.data.size > 0) audioChunksRef.current.push(e.data);
  };

  recorder.onstop = () => {
    const blob = new Blob(audioChunksRef.current, { type: 'audio/webm' });
    const url = URL.createObjectURL(blob);
    setAudioUrl(url);
    stopStreamTracks(stream);
    mediaStreamRef.current = null;
  };

  return recorder;
};

const startRecording = async () => {
  try {
    const stream = await navigator.mediaDevices.getUserMedia({ audio: true });
    const recorder = createMediaRecorder(stream);
    recorder.start();
    setIsRecording(true);
  } catch (err) {
    setError('Failed to start recording. Please try again.');
    setIsRecording(false);
  }
};
```

## Controlling Audio Flow

The core concept of the [Web Audio API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API) is the **audio graph**, a network of audio nodes connected together. Each node performs a specific function, like capturing input, applying effects, analyzing frequency data, or outputting to speakers.

Here's how nodes connect:

1. **Source nodes** - Generate or capture audio (like a microphone stream)
2. **Processing nodes** - Modify or analyze the audio (like gain control, filters, or custom processing)
3. **Destination nodes** - Output the audio (usually to speakers, but can also be to another stream)

Nodes are connected using the `.connect()` method, creating a chain through which audio flows. Below a small demo showcasing a StereoPannerNode to control left-right balance of the microphone input.

### AudioWorkletProcessor

AudioWorkletProcessor is where custom, real-time audio processing happens in the Web Audio API. It runs on the browser’s dedicated audio rendering thread (not the main UI thread). While it is not an AudioNode itself, it defines the processing behavior for a browser-managed node, which is exposed to the main thread as an AudioWorkletNode. The processor receives audio in small fixed-size blocks, applies your custom logic, and outputs the result back into the audio graph.

Below you can see such processor in action, receiving microphone input, injecting white noise, and sending the mixed output to the speakers.

<NoProse>
  <WhiteNoiseInjector client:load />
</NoProse>

```ts {43, 51}
// white-noise-processor.ts

class WhiteNoiseProcessor extends AudioWorkletProcessor {
  /**
   * The process method is called every 128 samples (approx. every 2.6ms at 48kHz).
   * @param {Array} inputs - An array of input ports (each containing channel arrays).
   * @param {Array} outputs - An array of output ports (each containing channel arrays).
   */
  process(inputs: Float32Array[][], outputs: Float32Array[][]) {
    const input = inputs[0]; // microphone input
    const output = outputs[0]; // speaker output

    /**
     * Most speakers are Stereo (2 channels: 0=Left, 1=Right).
     * We loop through the output channels to ensure we fill every speaker.
     */
    for (let channel = 0; channel < output.length; channel++) {
      const outputChannel = output[channel];

      /**
       * Fallback in case of a mono input.
       */
      const inputChannel = input[channel] || input[0];

      if (inputChannel) {
        /**
         * Iterating through the 128 floating-point samples in this block.
         */
        for (let i = 0; i < outputChannel.length; i++) {
          /**
           * Noise generation:
           * Math.random() generates 0 to 1.
           * Scale to -1.0 to 1.0 (the standard audio range).
           * Multiply by 0.05 to keep the noise at 5% volume.
           */
          const noise = (Math.random() * 2 - 1) * 0.05;

          /**
           * Mixing & preventing clipping:
           * Multiply the mic input by 0.9 to give it "headroom."
           * (Mic * 0.9) + (Noise * 0.05) = Max 0.95.
           */
          outputChannel[i] = inputChannel[i] * 0.9 + noise;
        }
      }
    }

    return true;
  }
}
registerProcessor('white-noise-processor', WhiteNoiseProcessor);
```

```ts {7-10}
// use-white-noise-injector.ts

const stream = await navigator.mediaDevices.getUserMedia({ audio: true });
const audioContext = new AudioContext();
await audioContext.audioWorklet.addModule(WhiteNoiseProcessor);

const whiteNoiseProcessorNode = new AudioWorkletNode(
  audioContext,
  'white-noise-processor',
);

const audioSourceNode = audioContext.createMediaStreamSource(stream);
const audioDestinationNode = audioContext.createMediaStreamDestination();
const mediaRecorder = createMediaRecorder(audioDestinationNode.stream);

// Mic -> White Noise Processor -> Media Recorder
audioSourceNode.connect(whiteNoiseProcessorNode);
whiteNoiseProcessorNode.connect(audioDestinationNode);
mediaRecorder.start();
```

## Audio Classification

For my use case, I needed an audio classification solution that could run entirely client-side. The goal was to have something that works on a mobile device without relying on a server.

### MediaPipe Studio

[MediaPipe Studio](https://mediapipe-studio.webapps.google.com/home) is a web-based tool for testing and customizing on-device machine learning models. For audio-based projects, the [Audio Classifier](https://mediapipe-studio.webapps.google.com/studio/demo/audio_classifier) allows you to perform real-time sound recognition directly in the browser.

#### Technical Details

- **Model:** It leverages **[YAMNet](https://www.kaggle.com/models/google/yamnet)**, a deep neural network capable of predicting 521 different audio event classes based on the AudioSet dataset.
- **Configuration:** You can adjust inference settings such as **Score threshold** (to filter out low-confidence predictions) and **Max results** (to limit the number of detected categories).
- **Supported SDKs:** MediaPipe provides native libraries across several environments: **Web:** JavaScript / TypeScript (see this [official CodePen example](https://codepen.io/mediapipe-preview/pen/wvxYYmy)), **Android:** Java / Kotlin & **Python**.

## Putting It All Together

Below a live demo of the audio classification in action. Try making different sounds into your microphone and see how the model classifies them in real-time!

</NoProse>

```ts
// use-audio-classification.ts

const SAMPLE_RATE = 16000;

const createAudioClassifier = async (): Promise<AudioClassifier> => {
  /**
    * WebAssembly is a type of code that can be run in modern web browsers.
    * It is a low-level assembly-like language with a compact binary format that runs with
    * near-native performance and provides languages such as C/C++, C# and Rust with a compilation target so that they can run on the web.
   */
  const audio = await FilesetResolver.forAudioTasks(
    'https://cdn.jsdelivr.net/npm/@mediapipe/tasks-audio@0.10.22-rc.20250304/wasm',
  );
  return AudioClassifier.createFromOptions(audio, {
    baseOptions: {
      modelAssetPath:
        'https://storage.googleapis.com/mediapipe-models/audio_classifier/yamnet/float32/1/yamnet.tflite',
    },
    maxResults: 5, // Limit to top 5 results
  });
};

const startClassification = async () => {
  try {
    setStatus('starting');
    ...
    audioContextRef.current = new AudioContext({ sampleRate: SAMPLE_RATE });
    await audioContextRef.current.audioWorklet.addModule(
      BufferedAudioProcessor,
    );
    bufferAudioProcessorNodeRef.current = new AudioWorkletNode(
      audioContextRef.current,
      'buffered-audio-processor',
      {
        processorOptions: {
          bufferSize: SAMPLE_RATE,
        },
      },
    );
    ...
    setStatus('running');
  } catch (error) {
    setStatus('error');
  }
};


// AudioWorkletProcessor transfers audio data to the main thread via messages.
const handleProcessorMessage = (event: MessageEvent) => {
  if (event.data.type === 'audio') {
    try {
      const results = audioClassifierRef.current.classify(
        event.data.data,
        SAMPLE_RATE,
      );

      const nextCategories = results[0].classifications[0].categories.map(
        (category) => {
          return {
            label: category.categoryName,
            score: category.score,
          };
        },
      );

      setCategories(nextCategories);
    } catch (error) {
      setStatus('error');
    }
  }
};
```

In the demo I am not actually recording audio. But you could easily add a MediaRecorder passing the destination stream from the AudioContext.

In my geocache I even added a score multiplier and the option to enable easy-mode as it proved really hard for a human to convincingly imitate a chicken. These 2 settings helped balance the difficulty and made the game more enjoyable.

## Sad News... 😞

After building the entire system and deploying it to production, I submitted the geocache for review on Geocaching.com. The reviewers rejected it.

The issue wasn't technical. The game worked perfectly. The problem was that Geocaching.com's current guidelines don't account for machine learning based caches.

I'm hoping Geocaching.com will eventually update their guidelines. Tech opens up entirely new types of challenges: sound recognition, image classification, gesture detection, all running client-side on a phone. For now, though, the geocache remains a technical demo rather than a live treasure hunt.

If you're considering building something similar, I'd recommend reaching out to your local reviewer first to discuss feasibility. The tech works great. It's the policy that needs catching up.
