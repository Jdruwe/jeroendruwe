I built a geocache that asks people to imitate a chicken. Cachers scan a QR code, get redirected to [toktoktok.pages.dev](https://toktoktok.pages.dev/), and make chicken sounds into their phone. The browser uses Google's MediaPipe to classify the audio in real-time. If the attempt is convincing enough, they get the combination to unlock the container.

This post covers how I built it, from capturing audio with the Web Audio API to running machine learning models in the browser.

## Geocache

If you're not familiar with geocaching, it's an outdoor treasure hunt using GPS coordinates. Someone hides a container, posts the coordinates online at [geocaching.com](https://www.geocaching.com/), and others use their phones or GPS devices to find it. There are over 3 million active geocaches worldwide.

Most are straightforward: find the container, sign the logbook, move on. But puzzle caches require solving challenges before you can access the container. These usually involve riddles, ciphers, or math problems solved at home before heading outside.

## Capturing Audio

The first step in building the audio classification system was getting access to the user's microphone. This is handled by the [Media Capture and Streams API](https://developer.mozilla.org/en-US/docs/Web/API/Media_Capture_and_Streams_API), which provides a standardized way to access media input devices in the browser.

The core of this API is [`getUserMedia()`](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia), a method that prompts the user for permission to access their microphone or camera. When you call it with `{ audio: true }`, the browser shows a permission dialog. If the user approves, you get a [`MediaStream`](https://developer.mozilla.org/en-US/docs/Web/API/MediaStream) object containing the audio track from their microphone.

```tsx
const stream = await navigator.mediaDevices.getUserMedia({ audio: true });
```

The `MediaStream` represents a stream of media content, in this case audio data from the microphone. This stream can be used in multiple ways—recording it with MediaRecorder, processing it with the Web Audio API, or even streaming it to another user in a WebRTC call.

## Recording Audio

Once I had access to the microphone via `getUserMedia()`, I needed a way to actually record and store the audio. [MediaStream Recording API](https://developer.mozilla.org/en-US/docs/Web/API/MediaStream_Recording_API) to the rescue.

The [`MediaRecorder`](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder) interface takes a `MediaStream` and records it into chunks of data. You attach event handlers to collect these chunks, and when recording stops, you combine them into a single audio file (typically a Blob) that can be played back or sent to a server.

Here's how MediaRecorder works in practice:

1. Get a MediaStream from `getUserMedia({ audio: true })`
2. Create a MediaRecorder instance with that stream
3. Attach event handlers for `ondataavailable` and `onstop`
4. Call `recorder.start()` to begin capturing
5. Collect chunks in `ondataavailable`
6. Call `recorder.stop()` when the user is done
7. In `onstop`, combine chunks into a Blob and create an object URL

Here's a basic recording demo to see it in action:

</NoProse>

```tsx
// use-audio-recorder.ts
const audioChunksRef = useRef<Blob[]>([]);

const createMediaRecorder = (stream: MediaStream) => {
  const recorder = new MediaRecorder(stream);

  recorder.ondataavailable = (e) => {
    if (e.data.size > 0) audioChunksRef.current.push(e.data);
  };

  recorder.onstop = () => {
    const blob = new Blob(audioChunksRef.current, { type: 'audio/webm' });
    const url = URL.createObjectURL(blob);
    setAudioUrl(url);
    stopStreamTracks(stream);
    mediaStreamRef.current = null;
  };

  return recorder;
};

const startRecording = async () => {
  try {
    const stream = await navigator.mediaDevices.getUserMedia({ audio: true });
    const recorder = createMediaRecorder(stream);
    recorder.start();
    setIsRecording(true);
  } catch (err) {
    setError('Failed to start recording. Please try again.');
    setIsRecording(false);
  }
};
```

## Audio Processing

Recording audio with MediaRecorder works fine for playback, but for real-time audio classification, I needed something more powerful. That's where the [Web Audio API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API) comes in.

The Web Audio API is designed for processing and synthesizing audio in the browser. Unlike MediaRecorder, which simply records chunks of audio, the Web Audio API gives you fine-grained control over audio streams through a modular system of **audio nodes**.

### Audio Nodes and the Audio Graph

The core concept of the Web Audio API is the **audio graph**—a network of audio nodes connected together. Each node performs a specific function, like capturing input, applying effects, analyzing frequency data, or outputting to speakers.

Here's how nodes connect:

1. **Source nodes** - Generate or capture audio (like a microphone stream)
2. **Processing nodes** - Modify or analyze the audio (like gain control, filters, or custom processing)
3. **Destination nodes** - Output the audio (usually to speakers, but can also be to another stream)

Nodes are connected using the `.connect()` method, creating a chain through which audio flows:

</NoProse>

```tsx
const audioContext = new AudioContext();
const source = audioContext.createMediaStreamSource(stream);
const gainNode = audioContext.createGain();
const destination = audioContext.destination;

source.connect(gainNode);
gainNode.connect(destination);
```

In this example, audio flows from the microphone → through a gain node (volume control) → to the speakers.

### AudioWorkletProcessor for Real-Time Processing

For the geocache, I needed to process audio in real-time without blocking the main thread. Running heavy audio analysis on the main thread would freeze the UI every time a chunk gets processed. The solution is [`AudioWorklet`](https://developer.mozilla.org/en-US/docs/Web/API/AudioWorklet).

AudioWorklet lets you write custom audio processing code that runs on a separate audio rendering thread. You define an [`AudioWorkletProcessor`](https://developer.mozilla.org/en-US/docs/Web/API/AudioWorkletProcessor)—a class that receives audio samples, processes them, and passes them along.

Here's the basic architecture:

1. Create an [`AudioContext`](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext) to manage the audio pipeline
2. Load your custom AudioWorkletProcessor module using [`audioContext.audioWorklet.addModule()`](https://developer.mozilla.org/en-US/docs/Web/API/Worklet/addModule)
3. Create an [`AudioWorkletNode`](https://developer.mozilla.org/en-US/docs/Web/API/AudioWorkletNode) that wraps your processor
4. Connect the microphone source → AudioWorkletNode → destination (or silence if you don't need playback)

The AudioWorkletProcessor receives audio data in the `process()` method, which is called automatically by the browser at regular intervals. Inside `process()`, you can collect audio samples and forward them for further analysis.

```tsx
// audio-worklet-processor.js (runs in worklet thread)
class AudioClassifierProcessor extends AudioWorkletProcessor {
  process(inputs, outputs, parameters) {
    const input = inputs[0];
    if (input.length > 0) {
      const samples = input[0]; // First channel
      // Send samples for classification
      this.port.postMessage({ samples });
    }
    return true; // Keep processor alive
  }
}

registerProcessor('audio-classifier-processor', AudioClassifierProcessor);
```

The key benefit of AudioWorklet is that this processing happens off the main thread. While the worklet is collecting and forwarding audio samples, the UI remains responsive—buttons work, animations run smoothly, and users can interact with the page without jank.

## MediaPipe Studio

[MediaPipe](https://ai.google.dev/edge/mediapipe/solutions/guide) is Google's collection of machine learning solutions designed to run efficiently in browsers, on mobile devices, and at the edge. It covers a wide range of tasks like pose detection, face mesh tracking, object detection, and, crucially for this project, audio classification.

What makes MediaPipe appealing is that it's built for real-world use cases. The models are optimized to run on-device, meaning no backend server is needed. Everything happens in the browser, which keeps latency low and avoids the cost and complexity of managing a server-side ML pipeline.

For this geocache project, I used MediaPipe's **Audio Classifier**, which can identify sounds in real-time and return confidence scores for various audio categories. The classifier is based on a model called **Yamnet**, which I'll cover in more detail below.

### Audio Classification

MediaPipe's audio classifier works by analyzing short windows of audio (typically a few seconds) and returning a list of detected sound categories along with confidence scores. For example, if you play a dog barking, the classifier might return "Dog" with a confidence score of 0.87, "Animal" with 0.72, and "Bark" with 0.65.

For my geocache, I specifically care about one category: chicken or rooster sounds. When a user makes a sound, the audio gets captured, passed through the worklet, fed into the MediaPipe classifier, and scored. If the confidence score for chicken-related sounds exceeds a certain threshold, the user gets the unlock code. If not, they try again.

One of the most helpful tools during development was the [MediaPipe Audio Classifier demo](https://mediapipe-studio.webapps.google.com/studio/demo/audio_classifier). It's a live web interface where you can test the classifier with your own audio input. I used it extensively to experiment with different sounds, test threshold values, and get a feel for how the model responds to various chicken imitations before integrating it into my site.

The integration itself is straightforward. MediaPipe provides a JavaScript library you can load in the browser. You initialize the classifier, feed it audio data from your worklet, and handle the classification results in a callback function. The library handles all the heavy lifting—loading the model, running inference, and returning predictions.

### Yamnet

**Yamnet** is the audio event detection model that powers MediaPipe's audio classifier. It's a neural network trained on [AudioSet](https://research.google.com/audioset/), a large-scale dataset of over 2 million labeled audio clips covering 521 different sound categories.

These categories range from the obvious—like "Dog," "Car," "Speech," and "Music"—to the surprisingly specific—like "Zipper," "Yodeling," and yes, "Chicken, rooster." The model was designed to recognize everyday sounds in uncontrolled environments, which makes it a good fit for real-world applications like this geocache project.

When Yamnet processes an audio clip, it outputs confidence scores for all 521 categories. Each score represents how confident the model is that a particular sound is present in the audio. Scores range from 0.0 (definitely not present) to 1.0 (very confident it's present).

For this project, I filter the results to focus on chicken and rooster-related categories. If the confidence score crosses a threshold—something like 0.4 or 0.5, depending on how strict I want to be—the user's imitation is accepted, and they get the combination to unlock the geocache container.

One interesting challenge was tuning that threshold. Too low, and random background noise might trigger a pass. Too high, and even decent chicken sounds get rejected. Testing with real users (and a lot of personal trial and error) helped me land on a threshold that felt fair and fun.
