<ItemLink {...wowForever} /> is Blizzard's new Classic+ server. The beta started
on September 17, 2026 and the official launch is on November 4. One of the new
things in Forever is how you name your character: instead of a single name, you
pick a **main name** and a **secondary name**.

It didn't take long before this screenshot was [shared on Reddit](https://www.reddit.com/r/classicwow/comments/1wpiqsb/wow_forever_senior_game_producer_says_to_not/):

<Image

The name filter let this one through. Two fields also give players a new trick: split a word across both fields and neither part looks bad on its own. "Pe" is fine. "Nis" is fine. "Pe Nis" is not.

I wanted to see if AI could do better here, so I built a small proof of concept: a copy of the Forever name picker with a **Name Guard** behind it. The Name Guard only judges content (sexual, racist or otherwise offensive). It does not check WoW's formatting rules like capitalization or allowed characters. It is powered by a single call to Jev.

## What is Jev?

<ItemLink {...jev} /> is a decision model from TypeSafe, available on OpenRouter
as `typesafe/jev-1.13`. It is not an LLM. It doesn't generate text. You send it
a JSON `state` and a set of typed questions, and it answers each question with a
probability:

- **noul**: a yes/no question, returns the probability of yes (0 to 1)
- **choice**: picks one option from a set you define, with a probability per option
- **score**: places the input on an ordered scale you define, and returns a probability-weighted position on it

### The State

Every check is one request to OpenRouter's decisions API. I call it with plain `fetch`, no SDK needed. The `state` describes the name in four ways:

```typescript
// server/jev.ts
const joinedName = (mainName + secondaryName)
  .toLowerCase()
  .replace(/[^a-z0-9]/g, '');

state: {
  first_name: mainName,
  surname: secondaryName,
  full_name: `${mainName} ${secondaryName}`,
  joined_name: joinedName,
},
```

`joined_name` is the key to the split-name trick. "Pe" + "Nis" becomes `penis`, and the banned word is suddenly visible. That is the only preprocessing I do. There are no word lists, no leetspeak decoding and no regex filters. Recognizing "Sh1t" as "Shit" is left to Jev.

### The Three Questions

The first question is the main signal: does this name deserve the <ItemLink {...banhammer} />? A `noul` gives the probability of yes.

```typescript
inappropriate: {
  type: 'noul',
  instructions: `Does this character name contain content that would get it banned from a game? ${JUDGING_CONTEXT}`,
  criteria: {
    true: 'The name contains sexual content, racist content, slurs, profanity or other offensive material.',
    false: 'The name is innocent and appropriate for a fantasy game.',
  },
},
```

The second question is a `choice` that explains _why_ a name is a problem.

```typescript
category: {
  type: 'choice',
  instructions: `What best describes this character name? ${JUDGING_CONTEXT}`,
  criteria: {
    clean: 'An innocent name appropriate for a fantasy game.',
    sexual: 'The name references sexual acts, anatomy or innuendo.',
    racist: 'The name contains racial or ethnic slurs, or racist references.',
    offensive: 'The name contains other offensive content such as profanity, violence or real-world hate.',
    inauthentic: 'The name itself is harmless but its spelling hides or imitates banned content, e.g. leetspeak or mangled casing.',
  },
},
```

The third question is a `score` on a three-step scale. The criteria array is ordered, so index 0 is the first entry. The result is a number between 0 and 2.

```typescript
severity: {
  type: 'score',
  instructions: `How severe is the content of this character name? ${JUDGING_CONTEXT}`,
  criteria: [
    'Perfectly fine as a character name',
    'Borderline, a human moderator would squint at it',
    'Clear ban-worthy violation',
  ],
},
```

### Repeating the Context

Because the questions are answered in parallel and can't see each other, context can't be shared between them. Every question has to say what it needs to know itself. That's why each instruction ends with the same `JUDGING_CONTEXT`:

```typescript
// Questions in a Jev request are answered independently, so every question
// must restate this context itself.
const JUDGING_CONTEXT =
  'The name was entered as two parts; also consider joined_name, which is both parts concatenated into one word, because banned words may only appear when the parts are joined. Judge the whole name, including words hidden by compound names, unusual casing or leetspellings.';
```

It feels repetitive, but it's the price of parallel questions. And since the instructions make up almost all the input tokens, it's also where most of the cost comes from (more on that below).

### Field Names Are Part of the Prompt

You might notice the keys in the state above mention `first_name` and `surname`, while the rest of the code talks about main and secondary names. That's because I didn't know yet what Forever called the fields. When I renamed everything to match the game, I also renamed the keys to `main_name` and `secondary_name`, reran my test names, and some verdicts changed.

I ran both versions several times against the same names:

| `state` keys                   | Kkk Master (noul)          | Mcsuck mahbal             | Gas Thejuice |
| ------------------------------ | -------------------------- | ------------------------- | ------------ |
| `first_name` / `surname`       | 0.88, 0.88, 0.88 (flagged) | 0.72 to 0.78 (flagged)    | 0.32 to 0.36 |
| `main_name` / `secondary_name` | 0.52, 0.70, 0.48 (flips)   | 0.59 to 0.62 (suspicious) | 0.23 to 0.26 |

Nothing else changed, only the key names. With `first_name` and `surname`, Jev was more confident and gave the same answer every run. With `main_name` and `secondary_name`, it was less sure and Kkk Master bounced between suspicious and flagged. My guess is that `first_name` / `surname` makes it obvious that this is a person's name, while "main name" is vague. I haven't proven that, but the lesson is clear:

<LoadingTip>
  `state` is not just data. The key names are part of the prompt, so treat them
  the way you'd treat your instructions.
</LoadingTip>

## From Probabilities to a Verdict

Jev gives me three answers. The <ItemLink {...nameGuard} /> turns them into one of three **Verdicts**: clean, suspicious or flagged. That decision lives in a small, pure function:

```typescript
// shared/verdict.ts
export const THRESHOLDS = {
  flagged: 0.7,
  suspicious: 0.4,
  severeBandStart: 1.5,
} as const;

export function decide(answers: JevAnswers): CheckResult {
  const { noul } = answers.inappropriate;
  const { score: severity } = answers.severity;

  let verdict: Verdict;
  if (noul >= THRESHOLDS.flagged) {
    verdict = 'flagged';
  } else if (
    noul >= THRESHOLDS.suspicious ||
    severity >= THRESHOLDS.severeBandStart
  ) {
    verdict = 'suspicious';
  } else {
    verdict = 'clean';
  }

  return { verdict, noul, category: answers.category.choice, severity };
}
```

A few things to note:

- `noul` decides almost everything. At 0.7 or above, the name is flagged.
- Severity can only raise a clean name to suspicious. It can never flag a name on its own.
- The category is **not used in the decision**. It's only there to explain the verdict.
- Suspicious is the "a human should look at this" zone. A plain yes/no would force every borderline pun into one side or the other.

## Where It Falls Short

### The Dog Whistle

Gas Thejuice came back **clean**, in every run. It doesn't contain a banned word. It's a racist dog whistle that only works when you say it out loud: it sounds like "gas the Jews". Jev judges what's written, and nothing written here is offensive.

One idea to catch these is a two-stage pipeline. First, ask a <ItemLink {...generativeLlm} /> what the name _sounds like_ and let it return a few readings. Then add those readings to the `state` as an extra field (say `sounds_like`) and let Jev judge them together with the name. That should catch a lot of these names, but it has a cost: a second model call, extra latency, and free-form text coming back into the pipeline, which is exactly what Jev let me avoid. I haven't built it yet.

### Hand-Picked Thresholds

The thresholds (0.7 and 0.4) are round numbers I picked by looking at 13 names. The Jev docs recommend choosing thresholds based on the cost of each kind of mistake, using labeled data. For a real game you'd want a much bigger set of names, including real names that were reported.

### Accented Letters

The regex that builds `joined_name` removes everything that isn't a to z or 0 to 9. That means "Pé" + "nis" becomes `pnis` instead of `penis`. Jev still sees the original parts, so it might catch it anyway, but I haven't tested that. Normalizing accents first (`.normalize('NFD')`) would fix it.
